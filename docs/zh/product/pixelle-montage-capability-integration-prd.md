# Pixelle OpenMontage 能力融入 PRD

版本：v0.1
日期：2026-06-30
状态：讨论稿
适用范围：Pixelle 视频生成、生产模板、Ops/Codex 生成闭环、未来 pipeline 扩展
目标读者：产品、后端、前端、Codex/自动化执行者
配套技术方案：`docs/zh/product/pixelle-montage-capability-integration-technical-plan.md`

## 1. 一句话目标

在不大规模重构 Pixelle 现有 pipeline 和 Ops 架构的前提下，吸收 OpenMontage 中高性价比的视频制作能力，让 Pixelle 从“能生成短视频”升级为“能稳定、可追踪、可扩展地生产多种视频形态”。

## 2. 背景

Pixelle 的长期目标不是做一个单条视频制作工具，而是成为个人和小团队可持续运营内容账号的生产系统。

当前 Pixelle 已经具备：

1. 项目、账号、实验、预测、发布和复盘等运营对象。
2. Codex/Ops 的自然语言运营入口。
3. `standard`、`custom`、`asset_based` 等视频生成 pipeline。
4. LLM、TTS、RunningHub/ComfyUI 图视频生成、HTML 模板、FFmpeg 合成、历史记录和发布能力。

OpenMontage 提供了更完整的视频制作工具箱和生产方法，包括素材清单、剪辑计划、质量检查、Remotion/HyperFrames 合成、真实素材检索、口播剪辑、长视频拆条等能力。

本 PRD 的核心判断是：

```text
Pixelle 不迁移 OpenMontage 产品和 agent-first 制作架构。
Pixelle 吸收 OpenMontage 的高价值能力模块。
```

## 3. 核心判断

### 3.1 Pixelle 的主心智

Pixelle 的主心智仍然是：

```text
我有一个项目/账号，需要持续选题、生产、发布和复盘内容。
```

不是：

```text
我每次都从零制作一条复杂视频。
```

因此，OpenMontage 能力融入 Pixelle 时必须满足三个原则：

1. 日常生成不能变复杂。
2. 常用能力要沉淀为固定生产模板。
3. 复杂视频制作能力只在需要时作为特定生产方式出现。

### 3.2 Agent-first 的边界

Pixelle 已经在 Ops 层引入了 agent-first：

```text
用户自然语言 -> Codex/Ops 理解项目、选题、实验、草稿、生成、发布和复盘
```

OpenMontage 的 agent-first 是另一层：

```text
agent 每次读 pipeline manifest、选择工具、写 checkpoint、推进制作阶段
```

Pixelle 不应该把第二种 agent-first 整体搬进视频生成执行层。

推荐边界：

```text
Pixelle Ops：agent-first
视频生成执行：production-template-first / pipeline-first
工具扩展：module-based
```

## 4. 核心概念

### 4.1 Pipeline

Pipeline 是视频生产流程类型，回答：

```text
这类视频怎么生产？
输入是什么？
经过哪些阶段？
输出是什么？
```

示例：

1. 标准短视频。
2. 素材驱动视频。
3. 真实素材 montage。
4. 口播剪辑。
5. 长视频拆条。

### 4.2 生产模板

生产模板是某个 pipeline 的固定配置版本，回答：

```text
这条固定生产线每一步具体怎么做？
使用哪个声音、素材方式、合成方式、字幕样式和质检规则？
```

示例：

1. `PetWoods 小红书日常短视频 v1`
2. `PetWoods 高质量解释视频 v1`
3. `真实素材科普短视频 v1`

用户日常生成时应该选择生产模板，而不是每次选择 provider。

### 4.3 生成方式

生成方式是生产模板内部某个阶段采用的技术方式。

示例：

1. 合成方式：HTML+FFmpeg、HyperFrames、Remotion。
2. 素材方式：AI 图像、AI 视频、用户素材、真实 stock/archive 素材。
3. 音频方式：Edge TTS、Fish Audio、ComfyUI TTS。

### 4.4 工具能力

工具能力是底层可被 pipeline 使用的能力。

示例：

1. TTS。
2. 图片生成。
3. 视频生成。
4. 素材检索。
5. 字幕。
6. 混音。
7. 调色。
8. 质量检查。

## 5. 产品目标

### 5.1 长期目标

Pixelle 应支持多种内容生产方式，但仍围绕运营闭环：

```text
项目/账号 -> 选题 -> 文案 -> 生产模板 -> 视频生成 -> 质量检查 -> 发布 -> 数据回收 -> 复盘
```

### 5.2 短期目标

短期目标不是扩展所有 OpenMontage pipeline，而是先提升现有视频生成链路的稳定性和表现力：

1. 让生成结果可检查。
2. 让每条视频的素材可追踪。
3. 让合成方式可扩展。
4. 让常用配置沉淀为固定生产模板。
5. 逐步支持更丰富的视频类型。

## 6. 非目标

第一阶段不做：

1. 不整体迁移 OpenMontage。
2. 不改成 OpenMontage 式每次动态选择 provider 的制作流程。
3. 不重写 Pixelle 的 pipeline 系统。
4. 不重构 Ops 状态机。
5. 不把 HyperFrames/Remotion 变成用户每次都要选择的前台问题。
6. 不优先做完整角色动画、完整数字人、完整长视频拆条、多语言本地化。
7. 不把 fallback、mock、placeholder 包装成真实生成成功。

## 7. 用户场景

### 7.1 日常账号短视频

用户希望快速稳定生成账号日常内容。

用户行为：

```text
确认选题 -> 审核字幕文案 -> 用默认日常生产模板生成 -> 检查成品 -> 发布/复盘
```

产品要求：

1. 不要求用户选择 provider。
2. 使用项目默认生产模板。
3. 生成失败必须明确失败原因。
4. 成品必须通过基础质量检查。

### 7.2 高质量解释视频

用户有一条重点内容，希望视觉表现比日常模板更强。

用户行为：

```text
选择高质量解释视频模板 -> 输入文案/主题 -> 生成更强动效视频
```

产品要求：

1. 可使用 HyperFrames 或 Remotion。
2. 保留 Pixelle 的文案、分镜、TTS 和 Ops 链路。
3. 只替换或增强合成层，不改变运营入口。

### 7.3 素材驱动视频

用户已有图片、产品图、宠物素材或短视频，希望系统包装成片。

产品要求：

1. 能记录素材来源和用途。
2. 能生成或补充支持画面。
3. 能生成字幕、BGM 和成片。
4. 能进入同一套历史和 Ops 状态。

### 7.4 真实素材风格视频

用户希望内容更像真实 footage montage，而不是 AI 图像拼接。

产品要求：

1. 第一阶段只做轻量版本。
2. 支持用户素材和少量 stock 素材。
3. 暂不要求完整 CLIP corpus 和复杂语义检索。

## 8. OpenMontage 能力纳入范围

### 8.1 第一优先级：必须纳入

| 能力 | 产品价值 | 技术性价比 |
|---|---|---|
| 质量检查 | 避免黑屏、无声、时长异常、字幕缺失视频进入发布 | 高 |
| 素材清单 | 每条视频可追踪用了哪些图、视频、音频、字幕和 BGM | 高 |
| 剪辑计划 | 合成前明确镜头顺序、时长、字幕、BGM 和转场 | 高 |
| 音频/字幕增强 | 提升短视频观看体验 | 高 |
| 合成方式抽象 | 为 HyperFrames/Remotion 接入留出口 | 中高 |

### 8.2 第二优先级：短期可做试点

| 能力 | 产品形态 | 说明 |
|---|---|---|
| HyperFrames 或 Remotion | 高质量解释视频模板 | 单点接入，不全局替换 |
| animated-explainer 思路 | 高质量解释视频生产模板 | 与 Pixelle `standard` 重叠高 |
| hybrid 思路 | 素材驱动增强模板 | 与 Pixelle `asset_based` 重叠高 |
| 轻量真实素材 montage | 新生产模板 | 先支持简单素材搜索/选择/拼接 |

### 8.3 暂缓纳入

| 能力 | 暂缓原因 |
|---|---|
| 完整 character-animation | 角色、rig、pose、动作时间线维护成本高 |
| 完整 avatar-spokesperson | 数字人质量、供应商、口型同步风险高 |
| 完整 localization-dub | 多语言、配音、字幕和口型同步超出当前主线 |
| 完整 clip-factory | 长视频拆条是另一类产品 |
| screen-demo | 除非 Pixelle 明确服务软件教程/产品演示 |

## 9. 阶段规划

### Phase 1：质量与可追踪性增强

目标：不改变现有 pipeline 执行逻辑，先把“生成完成”从一个宽泛状态升级为可验证、可解释、可追踪的结果状态。

产品问题：

1. 当前用户更关心“视频是否真的可用”，而不只是生成接口是否返回成功。
2. Ops 需要知道视频是否可以进入发布，而不是只知道任务是否跑完。
3. 后续引入 HyperFrames、Remotion、真实素材后，如果没有统一质检和素材记录，复杂度会快速失控。

用户价值：

1. 生成坏视频时，用户能明确看到问题原因。
2. 用户能知道一条视频用了哪些素材。
3. 发布前系统有最低质量门槛，减少人工反复检查。

范围：

1. 增加成片质量检查。
2. 增加素材清单。
3. 在历史和 Ops 中展示基础检查结果。
4. 将质量检查结果作为“是否可发布”的判断依据之一。

质量检查包括：

1. 文件存在。
2. 视频可播放。
3. 视频有音频。
4. 时长在合理范围。
5. 文件大小合理。
6. 抽帧非全黑。

素材清单至少记录：

| 素材 | 说明 |
|---|---|
| 最终视频 | `final.mp4` 或最终可交付视频 |
| 旁白音频 | TTS 生成音频 |
| 主要画面素材 | AI 生成图片、AI 生成视频或用户素材 |
| BGM | 使用的背景音乐 |
| 字幕/屏幕文案 | 用于合成的视频文字内容 |

前台展示要求：

1. 历史详情页显示质量检查状态：通过、警告、失败。
2. Ops asset check 能看到视频是否可发布。
3. 失败时展示用户能理解的原因，例如“视频没有音频”“成片不可播放”“抽帧检测到黑屏”。

验收标准：

1. 使用现有 `standard` pipeline 生成一条视频后，系统能产生质量检查结果。
2. 质量检查结果至少包含：文件存在、可播放、音频存在、时长、文件大小、抽帧黑屏。
3. 质量检查失败时，Ops 不应把该视频标记为可发布。
4. 每条新生成视频至少能追踪最终视频、旁白音频、主要画面素材和 BGM。
5. 历史详情或 Ops 详情中可以查看质量检查摘要。
6. 如果检查失败，用户能看到明确失败原因，而不是只看到“生成失败”。

暂不做：

1. 不接 HyperFrames 或 Remotion。
2. 不改现有 TTS、图片生成、视频生成 provider。
3. 不做跨任务素材库。
4. 不做复杂视觉质量评分。

技术影响：低。

依赖：

1. 现有生成任务能拿到最终视频路径。
2. FFmpeg/ffprobe 或等价检查工具可用。

风险：

1. 历史任务可能缺少完整素材路径。
2. 部分视频本身无音频，需要区分“允许静音”和“异常无声”。

### Phase 2：固定生产模板

目标：把常用生成方式固化成可命名、可复用、可版本化的生产模板，让用户每次只换内容，不重新选择 provider、workflow、模板和参数。

产品问题：

1. 用户不希望每次生成都选择 TTS、图像模型、视频模型、合成方式。
2. 项目需要沉淀自己的稳定生产线，例如 PetWoods 小红书日常视频。
3. OpenMontage 的多 provider 思路有价值，但在 Pixelle 中应该被固化到模板里，而不是暴露成每次生成的选择题。

用户价值：

1. 项目可以有默认生产线。
2. 用户日常生成只需要确认内容。
3. 不同质量档位可以通过不同模板表达，而不是通过临场配置表达。

范围：

1. 引入生产模板概念。
2. 支持项目默认模板。
3. 第一批模板：
   - `PetWoods 小红书日常短视频 v1`
   - `PetWoods 高质量解释视频 v1`

生产模板固定：

1. base pipeline。
2. entry。
3. TTS 设置。
4. 图/视频生成方式。
5. 合成方式。
6. 模板样式。
7. 字幕规则。
8. BGM 规则。
9. 质量检查规则。
10. 目标时长范围。
11. 平台画幅，例如小红书 9:16。
12. 是否允许降级，默认不允许静默降级。

模板示例：

| 模板 | 用途 | 默认合成方式 | 质量策略 |
|---|---|---|---|
| PetWoods 小红书日常短视频 v1 | 日常稳定产出 | 现有 HTML+FFmpeg | basic |
| PetWoods 高质量解释视频 v1 | 重点内容强化表现 | 待 Phase 3 接 HyperFrames 或 Remotion | strict |

用户流程：

```text
选择/确认选题
-> 审核字幕或文案
-> 选择生产模板或使用项目默认模板
-> 发起生成
-> 查看质量检查和成品
```

前台展示要求：

1. 模板有名称、适用场景和说明。
2. 用户能看到该模板是“日常快速”还是“高质量制作”。
3. 用户不需要看到 provider 细节，除非进入高级设置。
4. 如果模板依赖不可用，系统提示修复配置或切换模板。

验收标准：

1. 用户发起生成时可以选择生产模板。
2. 项目可以设置默认生产模板。
3. 生产模板能转化为现有 generation request。
4. 同一模板在不同输入下使用相同 provider、workflow、合成方式和质量规则。
5. 运行时不要求用户选择 provider。
6. 必需能力不可用时，系统明确报错，不静默换 provider。
7. 模板版本可识别，例如 `v1`、`v2`，历史任务能知道当时使用了哪个模板版本。

暂不做：

1. 不做复杂模板市场。
2. 不做非技术用户可自由编辑全部底层参数的界面。
3. 不为每个生产模板新增一个底层 pipeline class。
4. 不做自动 provider 推荐 UI。

技术影响：中低。

依赖：

1. Phase 1 的质量检查和素材清单。
2. 当前 generation request 能承载模板固定参数。

风险：

1. 模板概念可能和 pipeline、workflow、HTML 模板混淆。
2. 模板配置过多会增加维护成本。

应对：

1. 产品文案统一使用“生产模板”。
2. 初期只内置少量模板。
3. 高级参数先内部配置，不做开放编辑。

### Phase 3：合成方式扩展

目标：在不影响日常生成稳定性的前提下，为一个高质量生产模板接入新的合成方式，让成片表现从固定模板拼接升级到更强动效或组件化视频。

产品问题：

1. 当前 HTML+FFmpeg 适合稳定日常生成，但视觉表现上限有限。
2. OpenMontage 的 HyperFrames/Remotion 价值主要体现在合成层。
3. 新合成方式不应全局替换现有链路，而应先服务高质量模板。

用户价值：

1. 用户可以为重点内容选择更强表现力模板。
2. 日常内容仍保持简单、稳定、快速。
3. Pixelle 能覆盖更高质量的视频形态。

范围：

1. 引入合成方式抽象。
2. 支持现有 HTML+FFmpeg 作为默认合成方式。
3. 选择 HyperFrames 或 Remotion 做一个试点模板。

建议：

1. 如果优先做强动效和视觉包装，先试 HyperFrames。
2. 如果优先做结构化解释、图表、组件复用，先试 Remotion。

试点选择标准：

| 选择 | 适合场景 | 试点价值 |
|---|---|---|
| HyperFrames | 小红书强动效、关键词动画、品牌包装、视觉冲击 | 快速提升视觉表现 |
| Remotion | 结构化解释、数据图表、组件化字幕、可复用视频组件 | 长期模板体系更稳定 |

第一版建议只选择一个 runtime 试点，避免同时引入两套复杂度。

产品细节：

1. 高质量模板名称中不出现技术名，除非高级模式。
2. 用户看到的是“高质量动效视频”或“结构化解释视频”。
3. 模板详情中可以说明“渲染耗时更长，视觉表现更强”。
4. 失败时返回“合成失败”及可理解原因。

验收标准：

1. 日常模板仍走现有 HTML+FFmpeg。
2. 至少一个高质量模板可以走新合成方式生成成片。
3. 新合成方式失败时，不影响现有日常生成。
4. 成片仍进入同一套质量检查、历史和 Ops。
5. 生成历史能记录使用了哪种合成方式。
6. 不允许新 runtime 失败后静默切回 HTML+FFmpeg 并标记成功。
7. 同一输入下，高质量模板的成片表现与日常模板有明显差异。

暂不做：

1. 不全局替换现有合成方式。
2. 不同时接入 HyperFrames 和 Remotion。
3. 不把 runtime 选择暴露给普通用户。
4. 不做复杂自定义动效编辑器。

技术影响：中。

依赖：

1. Phase 2 的生产模板。
2. Phase 1 的质量检查。
3. 可用的 Node/渲染环境或对应 runtime 依赖。

风险：

1. 新 runtime 环境依赖更复杂。
2. 渲染失败原因可能更难解释。
3. 新成片耗时可能明显增加。

应对：

1. 只绑定试点模板。
2. 失败不降级伪装成功。
3. 模板说明中提前提示耗时和质量定位。

### Phase 4：轻量真实素材 montage

目标：引入真实素材风格视频能力，但先做轻量版，验证用户是否需要 AI 生成画面之外的真实 footage 内容。

产品问题：

1. 当前 Pixelle 主要依赖 AI 生成图片/视频或用户上传素材。
2. 部分内容更适合真实素材，例如科普、生活方式、品牌氛围、宠物场景。
3. OpenMontage 的完整 documentary montage 很重，第一版不应直接全量实现。

用户价值：

1. 视频画面更真实，减少“AI 感”。
2. 可以生产更像纪录片、混剪、氛围短片的内容。
3. 丰富 Pixelle 的视频类型。

范围：

1. 新增 `真实素材科普短视频 v1` 生产模板。
2. 支持用户素材和少量 stock 素材。
3. 支持简单镜头选择、拼接、字幕、BGM 和质检。
4. 暂不做完整 CLIP corpus。

素材来源第一版建议：

1. 用户上传素材。
2. 少量可配置 stock/source 素材。
3. 项目内本地素材库。

产品流程：

```text
输入主题/脚本
-> 生成镜头需求
-> 从可用素材中选择镜头
-> 生成字幕/BGM/旁白
-> 拼接合成
-> 质量检查
```

第一版 montage 能力边界：

1. 支持 3-8 个镜头。
2. 支持简单 cut 或 fade 转场。
3. 支持统一 BGM。
4. 支持字幕或少量标题卡。
5. 支持素材来源记录。

验收标准：

1. 用户可以用固定模板生成真实素材风格短视频。
2. 素材来源可记录到 asset_manifest。
3. 成片通过质量检查。
4. 不影响现有 `standard` 和 `asset_based`。
5. 如果素材不足，系统明确提示素材不足，而不是生成低质量占位视频。
6. 生成结果能体现真实素材拼接，而不是仍然只走 AI 图片模板。

暂不做：

1. 不做完整 CLIP 语义素材库。
2. 不做大规模素材抓取。
3. 不做复杂版权工作流。
4. 不做完整 OpenMontage documentary pipeline。
5. 不做多小时素材自动剪辑。

技术影响：中。

依赖：

1. Phase 1 的 asset_manifest。
2. Phase 2 的生产模板。
3. Phase 3 中合成方式或 FFmpeg 拼接能力稳定。

风险：

1. stock 素材质量不稳定。
2. 素材版权和来源记录需要清晰。
3. 缺素材时用户体验可能差。

应对：

1. 第一版优先支持用户素材和本地素材。
2. 外部素材必须记录来源。
3. 素材不足时阻断生成并提示补素材。

### Phase 5：新生产方式评估

目标：基于真实用户需求和前四个阶段的基础能力，再决定是否扩展更重的新生产方式。

产品问题：

1. OpenMontage 有很多 pipeline，但 Pixelle 不应该一次性纳入。
2. 新生产方式会引入新的输入、状态、素材和质检要求。
3. 必须先验证是否服务 Pixelle 的内容运营主线。

候选：

1. 口播自动剪辑。
2. 长视频拆短视频。
3. 产品演示视频。
4. 本地化配音。
5. 数字人/角色动画。

进入条件：

1. 有明确用户场景。
2. 能服务 Pixelle 内容运营主线。
3. 能复用生产模板和 Ops 状态。
4. 不显著增加维护成本。

评估维度：

| 维度 | 说明 |
|---|---|
| 用户需求强度 | 是否有明确用户频繁提出 |
| 与运营闭环关系 | 是否能进入选题、生成、发布、复盘链路 |
| 复用程度 | 是否复用 asset_manifest、edit_decisions、quality_review |
| 技术复杂度 | 是否需要新模型、新环境或新状态机 |
| 维护成本 | 是否会引入长期 provider 和质量风险 |

候选优先级建议：

| 生产方式 | 建议优先级 | 原因 |
|---|---|---|
| 口播自动剪辑 | 中 | 如果用户已有口播素材，价值明确 |
| 长视频拆短视频 | 中 | 适合内容复用，但产品形态独立 |
| 产品演示视频 | 中低 | 取决于 Pixelle 是否服务软件/工具类内容 |
| 本地化配音 | 中低 | 有价值但不是当前主线 |
| 数字人/角色动画 | 低 | 质量和维护成本高 |

验收标准：

1. 每个候选方向都有独立需求评估。
2. 新生产方式必须说明它是新 pipeline，还是现有 pipeline 的生产模板。
3. 新生产方式必须复用前四阶段建立的素材、剪辑、合成和质检能力。
4. 未通过评估的方向不进入开发排期。

暂不做：

1. 不在没有用户需求的情况下扩展重型 pipeline。
2. 不因为 OpenMontage 有某个 pipeline 就默认纳入 Pixelle。
3. 不绕过生产模板和质量检查直接接入新工具。

## 10. 成功指标

1. 生成失败误判成功的比例下降。
2. 每条视频可追踪素材和质量检查结果。
3. 用户日常生成时不需要选择 provider。
4. 至少一个高质量模板产出明显优于当前模板的视频。
5. 新能力不影响现有日常生成稳定性。
6. Ops 流程仍保持：选题 -> 文案 -> 生成 -> 检查 -> 发布/复盘。

## 11. 风险与约束

### 11.1 产品风险

风险：能力扩展后前台复杂度上升。

应对：

1. 前台只暴露生产模板。
2. provider、runtime 和检查项放在模板配置里。
3. 日常生成不出现技术选择题。

### 11.2 技术风险

风险：合成 runtime 接入导致生成链路不稳定。

应对：

1. 新合成方式只绑定试点模板。
2. 默认模板继续走现有 HTML+FFmpeg。
3. 失败时明确标记，不静默降级。

### 11.3 范围风险

风险：把 OpenMontage pipeline 全部纳入导致项目失控。

应对：

1. 按能力模块纳入，不按 OpenMontage pipeline 全量迁移。
2. 每阶段都必须有独立验收价值。
3. 暂缓重型能力。

## 12. 最终结论

当前阶段应采用渐进式路线：

```text
先增强现有 pipeline 的可靠性
再沉淀固定生产模板
再接入一个新合成 runtime
再试点轻量真实素材 montage
最后按需求扩展新生产方式
```

产品原则：

```text
复杂能力后台化
常用能力模板化
日常使用简单化
技术扩展渐进化
```
