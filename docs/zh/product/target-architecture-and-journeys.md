# Pixelle 目标架构与用户动线设计

日期：2026-07-05
性质：正向设计文档——从产品本质推导最合理形态，不受当前实现约束；末章给出从现状到目标的迁移路径。

---

## 一、设计前提（从产品定位文档继承）

产品是**单运营者的 AI 短视频内容工厂**，经营循环是：选题 → 内容 → 出片 → 发布 → 数据 → 复盘。人和 agent 是同一工厂的操作员。三类资产：内容、模板、成片。

由此得出三条设计公理：

1. **内容条目（ContentItem）是一等公民。** 一个选题从想法到发布后数据，是同一个对象的生命周期，不是散落在五个页面里的五条记录。
2. **生产是内容生命周期上的一次"操作"，不是入口。** 单条/批量只是选中几个条目的区别；审核只是某个状态迁移是否需要人点头。
3. **人和 agent 操作同一块板。** agent 能做的一切（补选题、起草、出片、排期）人都能看见、能拦截；自动化程度是每个状态迁移上的一个档位，不是另一套系统。

**当前架构（工具形）的根本局限**：导航按生产动作组织（新建视频/任务/作品库），用户每次进来都要回答"我现在要用哪个工具"，而他真正的问题是"**我的内容都到哪一步了？今天该推进什么？**"跨页面的断点（选题记在别处、确认稿不可复用、发布完数据看不见）都源于没有内容条目这个中心对象。

## 二、目标信息架构

```
工作台（首页，看板）   ← 运营者每天生活的地方
├── 列：选题池 → 草稿 → 待确认 → 生产中 → 待发布 → 已发布
├── 条目卡：状态、语言变体、进度、数据摘要
└── 多选操作条：生成草稿 / 用模板出片 / 排期发布

内容库                 ← 所有条目与确认稿，可搜索、可复用、可再次出片
模板库                 ← 生产能力：默认配置、预览、成本档位（含迁移状态，内部视角收进详情）
发布日历               ← 跨渠道排期的时间视图（看板"待发布"列的另一投影）
设置                   ← 接入、项目、自动化档位、专家模式
```

导航从"四个工具"变成"一块板 + 三个资产库 + 设置"。任务中心消失——生产进度就是看板"生产中"列本身（全局角标保留）；作品库并入条目详情（成片是条目的产物，不是独立世界）。

### 内容条目状态机

```
idea（选题池）
  → drafting（AI 起草中）→ draft_ready（草稿）
  → pending_review（待确认，可跳过）→ confirmed（已确认）
  → producing（生产中）→ produced（待发布）
  → scheduled → published（已发布）
  → measured（有数据）
任意状态 → archived
```

关键性质：
- **多语言是条目的变体维度**，不是新条目：一个条目携带 N 个语言变体，每个变体独立走 确认→出片→发布，卡片上以徽章呈现（图例中"中文 待审 / EN 已确认"）。
- **可跳过与可回退**：直接粘贴现成文案 = 建条目时直接落在 confirmed；出片失败回 confirmed 可换模板重出；发布后可再次出片（同一内容 × 不同模板 = 多个产物挂在同一条目下）。
- **每次迁移记事件**（复用 ops 已有的事件模型），谁做的（人/agent）、什么时候、用了什么模板——复盘的原材料。

### 自动化档位（人机同板的机制）

每个项目对每个状态迁移配置三档：**手动**（人点按钮）/ **审核制**（agent 做完停在待确认）/ **自动**（agent 直通）。例如成熟期的日常内容：选题→草稿 自动，草稿→确认 审核制，确认→出片→排期 自动。UI 上 agent 推进的卡片带 agent 标记，运营者的日常工作从"操作每一步"退化为"处理待确认列 + 看数据"——这是这个产品规模化的终局形态。

## 三、目标用户动线

### 动线 1 · 每日十分钟（最高频，产品的"心跳"）

1. 打开工作台，一眼看五列的数字和异常色（失败的卡片红角标）。
2. 处理「待确认」列：逐卡打开抽屉审文案（改标题/分镜、勾语言）→ 确认（自动流入生产）或打回。
3. 扫「已发布」列的新数据徽章，表现好的点「衍生选题」回选题池。
4. 关掉。生产、排期、发布都在后台自己走。

**完成判据**：待确认清零。设计目标：≤10 分钟。

### 动线 2 · 周一规划（批量入料）

1. 工作台 →「添加选题」：粘贴一批（一行一条）或从数据建议里勾选，设定语言组合（如 中文+EN）。
2. 多选这批卡片 → 操作条「生成草稿」。
3. 之后由动线 1 消化。

### 动线 3 · 出片（生产就是一个动作）

1. 在任何列多选已确认的条目（1 个或 50 个——单条和批量在这里合并）。
2. 操作条「出片」→ 弹出**生产提交面板**（已有组件）：选模板 + 默认摘要 + 专家覆盖 + 数量与额度预告。
3. 确认 → 卡片流入「生产中」，卡上直接显示进度条；失败卡片红标，点开重试或换模板。

### 动线 4 · 发布与排期

1. 「待发布」列的卡片：点「排期」选时间与渠道（默认取项目的发布节奏，如每天 09:00 顺延），或切到发布日历拖到某天。
2. 到点自动发布（Buffer），卡片流入「已发布」；发布失败红标回列。

### 动线 5 · 数据与复盘（闭环）

1. 发布 24h/7d 后数据自动回填到卡片（赞/收藏/涨粉，来源 Buffer/平台 API 或人工录入兜底）。
2. 已发布列可按表现排序；点开条目看「同内容不同模板」的产物对比——**模板好坏第一次变得可度量**。
3. 复盘动作：好内容 →「衍生选题」；好模板 → 去模板库调成默认。

### 动线 6 · 素材与特效类内容

素材类条目 = 建条目时附素材文件（拖拽即建卡），出片时兼容模板自动过滤为素材/i2v/数字人类模板。动线与 3 相同——特殊生成不再是"另一个页面"，只是"这张卡能用的模板不同"。

## 四、目标技术架构

```
前端                        后端                          存储
工作台看板 ──┐         ContentItem API（CRUD+迁移）── content-items 存储（沿用 JSON/SQLite 风格）
条目抽屉    ├── 状态 ── 状态机 + 事件日志（复用 ops.OpsEventType）
内容库      │            │
生产提交面板 ┴────────── 生产模板体系 compile_request（已统一，R1-R4 ✅）
发布日历 ──────────── publish API + 排期器（Buffer，已有）
数据卡片 ──────────── metrics 采集 worker（marketing/ 已有骨架）→ 回填条目
自动化档位 ──────────── transition rules（project 级配置）→ agent 走同一 API
```

新增的只有两块：**ContentItem 实体（含状态机与事件）** 和 **transition rules**。生产、发布、模板、任务轮询全部复用现有层——这正是先做生产提交层统一的原因：它是这个架构的地基。

关键设计决策与理由：

| 决策 | 理由 |
| --- | --- |
| 条目为中心而非任务为中心 | 任务是易逝的（跑完就没了），内容是资产；复盘必须以内容为主键 |
| 看板而非列表/表单 | 运营者的核心问题是"都到哪一步了"；看板把状态即视化，且天然承载多选批量 |
| 多语言=变体而非多条目 | 审核、对比、复盘都以"同一内容"为单位；拆成多条目会让板爆炸 |
| 任务中心/作品库降级为投影 | 减少一级概念；进度和成片都在条目上，全局角标保留即可 |
| 自动化按"迁移"配置而非全局开关 | 信任是逐步建立的；先自动化起草，最后才自动化发布 |
| agent 与人共用 ContentItem API | 避免两套真相；事件日志天然记录人机分工 |

## 五、取舍与非目标

- **不做多人协作**（评论、指派、权限）：单运营者 + agent，事件日志足够；多人是另一个产品。
- **不做完整数据分析平台**：卡片级核心指标 + 排序即可，深度分析交给平台后台。
- **保留极简模式**：看板的每个动作都有对应 API/页面直达（如 `/create` 直接建卡出片），不强迫用户理解看板才能出第一条片。
- **最小替代方案**（如果认为看板过重）：保持现有四区导航，只加「内容库」页 + 条目状态字段。此方案成本约为看板的 1/3，但"今天该做什么"仍要用户自己跨页拼装，且自动化档位没有落点。**建议直接做看板**——这个产品的差异化恰恰在"经营流水线"而不在"生成器"。

## 六、从现状到目标的迁移路径

现状（R1-R4 后）已具备：统一生产提交层、模板默认体系、全局任务轮询、发布链路、审核草稿持久化。缺的是中心对象和它的视图。

- **M1 · 条目地基（后端）**：ContentItem 实体 + 状态机 + 事件日志；把现有数据映射进来（draft_set → 待确认条目，generation task → 生产中/待发布，publish record → 已发布）。旧 API 不动，新 API 平行提供。
- **M2 · 工作台只读版**：看板页读条目渲染五列 + 条目抽屉（内容、变体、产物、发布记录聚合视图）；导航加「工作台」，其余页面保留。此时即可验证"每日十分钟"动线。
- **M3 · 看板可操作**：添加选题、多选操作条（生成草稿/出片/排期，复用 ProductionSubmitPanel）、确认/打回；「新建视频」Gallery 降级为添加条目的一种方式；任务中心并入看板。
- **M4 · 发布日历 + 数据回填**：排期视图；metrics worker 回填卡片；「衍生选题」。
- **M5 · 自动化档位**：transition rules + agent 走 ContentItem API；工作台出现 agent 标记。

每个 M 独立可发布、可回退；M2 结束就应该用"每日十分钟"动线做一次真实自测，不达标就修完再往下走。

## 七、开放决策（需要你拍板）

1. **看板 vs 最小替代**（第五章）——建议看板，影响 M2-M5 全部。
2. **数据回填来源**：小红书无公开 API，首期用 Buffer 统计 + 人工录入兜底，还是先只做人工录入？（影响 M4 范围）
3. **多语言变体的发布归属**：不同语言发不同渠道账号时，排期按变体还是按条目聚合展示？（M4 交互细节，可到时再定）
